# VIBE CMS Site Packages and Studio-Managed API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Extend the existing single-site CMS so a studio can compile one bespoke Site Package into each isolated customer installation, edit it through the existing CMS API, and publish a static release to customer-controlled S3-compatible hosting.

**Architecture:** Keep every customer installation single-site and isolated by database, secrets, host name, and destination credentials. Extract the current hard-coded block validation/editor/renderer choices behind a build-selected Site Package, preserve the current immutable snapshot and blue/green publication pipeline, and keep public pages independent from CMS runtime availability.

**Tech Stack:** Bun 1.3.14, TypeScript 6, Zod 4, Hono, Prisma/PostgreSQL 18, React 19, Astro 5, Tailwind CSS 4, Docker Compose, S3-compatible object storage.

**Spec:** `docs/superpowers/specs/2026-08-25-vibe-cms-site-packages-api-design.md`

## Global Constraints

- Reuse the existing CMS API, drafts, revisions, preview, approval, publication, builder authentication, media copy, `StaticUploadPort`, and blue/green promotion.
- A customer installation contains exactly one build-selected Site Package and never accepts a package ID from a browser request or snapshot as a selection instruction.
- Preserve the stored block shape `{ id, type, data }`; do not add arbitrary HTML, CSS, JavaScript, iframe, remote module, or executable manifest fields.
- Core blocks remain valid and become registry entries; new block types are code-defined package extensions.
- Public pages remain static and must not fetch primary content from the CMS API at request time.
- Customer builds and runtime images must contain only shared core plus the selected customer's package.
- The first certified destination is S3-compatible blue/green static hosting; SFTP, FTP, generic booking, payments, CRM inbox, multi-tenancy, DRM, Redis, Kubernetes, and a package marketplace are out of scope.
- Use TDD for contracts, validation, persistence, routing, build selection, publication, and migration behaviour.
- Do not stage or modify `.playwright-cli/`, `.ux-audit/`, `output/`, or `webapp/.21st/`.
- Do not run cloud apply. Production credentials, domain values, and customer data must not enter the repository, tests, logs, or screenshots.

- [ ] **Step 3: Implement strict descriptors and schema factories**

Use a stable package ID and semver-like package version:

```ts
export const sitePackageDescriptorSchema = z.object({
  id: z.string().regex(/^[a-z][a-z0-9-]{1,62}$/),
  version: z.string().regex(/^\d+\.\d+\.\d+$/),
  schemaVersion: z.number().int().positive(),
}).strict()

export type RegisteredContentBlock = {
  id: string
  type: string
  data: unknown
}

export function createContentBlockSchema(definitions: readonly CmsBlockContractDefinition[]) {
  const byType = requireUniqueDefinitions(definitions)
  for (const definition of definitions) definition.dataSchema.parse(definition.defaultData)
  return z.object({
    id: z.string().trim().min(1).max(64),
    type: z.string().trim().min(1).max(80),
    data: z.unknown(),
  }).strict().transform((block, context) => {
    const definition = byType.get(block.type)
    if (!definition) {
      context.addIssue({ code: 'custom', path: ['type'], message: 'Unknown CMS block type' })
      return z.NEVER
    }
    return { ...block, data: definition.dataSchema.parse(block.data) }
  })
}
```

## Final completion criteria

Implementation is complete only when all of the following are evidenced:

- No core CMS feature was duplicated.
- A bespoke package adds a block without editing backend, admin, or website type switches.
- The customer can edit declared calculator parameters but not its formula or design.
- Snapshot package mismatch fails before build/upload.
- Final runtime images contain only the selected package.
- Published static pages work while CMS/API is unavailable.
- Customer data and credentials are isolated by installation.
- Failed migration, build, upload, or promotion preserves the previous public release.
- The reference package passes mobile/desktop browser QA and SEO-visible HTML checks.
- VDS build concurrency is bounded and capacity results are recorded rather than guessed.
- A context-free agent can create the next package by following `docs/SITE_PACKAGES.md` and `docs/CMS_SITE_WORKFLOW.md`.
