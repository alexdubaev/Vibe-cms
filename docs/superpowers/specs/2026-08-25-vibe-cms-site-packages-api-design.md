# VIBE CMS Site Packages and Studio-Managed API Design

## Status

Approved in conversation on 2026-08-25 as the architectural basis for the next implementation plan.
This document narrows and supersedes the hosting and delivery assumptions in
`docs/specs/vibe-cms-module-design.md`. Existing CMS content, permission, revision, preview, and
publication decisions remain in force unless this document explicitly changes them.

## Purpose

Allow a studio to create many visually and functionally different public sites with the
`vibe-landing` workflow while reusing one VIBE CMS core. Each customer receives a fixed bespoke
design and a constrained CMS editor for that design. The studio keeps the source repository and
operates the CMS/API. Publication produces a static site on customer-controlled hosting, so normal
visitor traffic does not depend on the studio CMS.

Examples include an auto-service site with a repair calculator, a barber site with appointment
booking, a ceiling site with a price calculator, and a real-estate site with a mortgage calculator.
The CMS must not force these sites into one visual template or require changes to CMS core for each
new design.

## Confirmed product decisions

- The studio, not the customer, creates the site's design and functional modules.
- Each customer sees one fixed design. The customer cannot switch themes or edit CSS, JavaScript,
  Astro components, formulas, or arbitrary schemas.
- The customer may edit only fields declared by that site's package: text, images, links, menus,
  contacts, SEO, collection content, safe visual variants, section order, and selected business
  parameters.
- A new site may reuse core blocks, add bespoke block types, or add bespoke interactive modules.
- A bespoke module is code owned by the studio. The CMS edits its declared data; it does not invent
  or execute customer-supplied code.
- The source repository remains private. A Git repository stores source and drives deployment; it
  is not the API runtime.
- The studio operates the CMS/API on its server. The first production model uses one isolated
  installation per customer rather than one multi-tenant CMS database.
- Published site files and public media are delivered to hosting controlled for that customer.
- Public pages are static by default. Visitor requests do not read CMS content through a runtime
  API.
- Dynamic runtime APIs exist only for capabilities that require them, such as booking or form
  submission. Pure calculators run in the visitor's browser.
- Initial infrastructure is expected to fit a 4 vCPU, 8 GB RAM, 80 GB VDS for a small pilot, with
  bounded build concurrency, external media storage, external backups, and measurement before
  scaling. This is a capacity hypothesis, not a guaranteed customer count.

## What already exists and must be reused

The implementation must extend these mechanisms instead of replacing them:

- owner/editor roles and backend-enforced capabilities;
- page and collection drafts;
- autosave and optimistic revision conflicts;
- immutable revisions and restore-to-draft;
- media upload tickets, metadata, references, and safe public descriptors;
- authenticated preview;
- approval and publication policy;
- immutable publication snapshots;
- publication state, retry, outbox, build authentication, nonce protection, and revision markers;
- Astro build from `CMS_SNAPSHOT_FILE`;
- static upload through `StaticUploadPort`;
- blue/green publication and previous-release retention;
- current core block schemas and the page payload shape `{ id, type, data }`;
- page block add, remove, duplicate, and reorder behaviour in the web app;
- current site settings, menus, redirects, collections, SEO inputs, and media IDs.

The current hard-coded block editor and renderer become registry consumers. They are not replaced
by a second page editor or publication pipeline.

## Explicitly changed assumptions

The original CMS design says every customer receives an independent codebase and infrastructure
and that there is no CMS subscription. That is no longer the default commercial or operational
model.

The new default is:

- one private studio source repository;
- one selected Site Package per customer build;
- one isolated customer installation on studio-managed infrastructure;
- one database and one credential set per customer installation;
- customer admin access without repository or server-shell access;
- static publication to the customer's destination;
- recurring hosting/maintenance terms handled commercially outside this technical specification;
- an export or separate handoff path if the customer later leaves the managed service.

Self-hosted customer installations remain a possible future delivery option, not the first
implementation target.

## Architecture

```text
Private studio repository
  ├── VIBE CMS core
  ├── shared core block definitions
  └── customer Site Packages
              │ selected during build/deploy
              ▼
Studio-managed VDS
  ├── reverse proxy and TLS
  ├── customer A admin + API + database configuration
  ├── customer B admin + API + database configuration
  ├── customer C admin + API + database configuration
  └── bounded website build execution
              │ signed publication input
              ▼
Customer destination
  ├── static HTML/CSS/JS
  ├── immutable public media
  └── CDN/domain/SSL
```

Each installation is single-site. No request accepts a customer-selected `tenantId`, and CMS
tables do not gain a multi-tenant discriminator in this phase. Routing and deployment configuration
choose the installation before authentication, and every process receives only that installation's
database and storage credentials.

The VDS may run several installations, but isolation is logical and operational:

- separate database and restricted database user;
- separate environment secret set;
- separate private media scope;
- separate publication destination credentials;
- separate host name;
- separate backups and restore procedure;
- resource limits per container or process.

PostgreSQL may be one server process initially, but each customer uses a distinct database and role.
Cross-customer SQL access is not granted.

## Site Package

A Site Package is a code-owned extension selected for exactly one customer installation. It is the
bridge between a bespoke `vibe-landing` site and the generic CMS core.

The package exposes a typed manifest with:

- stable package ID;
- human-readable internal name;
- package version;
- persisted schema version;
- supported core block types;
- bespoke block definitions;
- default page and settings payloads for first bootstrap;
- safe visual variants;
- admin field descriptors or a package-owned editor component;
- Astro renderers;
- optional browser-interaction modules;
- optional backend capability declarations;
- content migrations;
- package-specific validation and acceptance tests.

The package is selected through deployment configuration and compiled into the customer build. A
publication snapshot may identify the selected package and version, but it must never be allowed to
load a different package dynamically from a URL or customer input.

Customer build artifacts and runtime images contain only the selected package and shared core.
They must not bundle another customer's package, assets, initial content, or deployment settings.

At startup and build time, the configured package ID must match the deployed package. A mismatch
fails closed before draft mutation or publication.

### Core blocks and bespoke blocks

Core block contracts remain the default. A package may:

1. permit or hide a core block type;
2. provide package-specific defaults and safe variant choices;
3. provide a bespoke renderer for that core semantic block;
4. add a new code-defined block when the core catalogue cannot express the feature.

Adding a bespoke block does not require changing CMS core switch statements. It requires a package
definition, schema, defaults, editor description, renderer, migration policy, and tests.

### Admin field model

The registry supports a deliberately limited field vocabulary:

- short text;
- long or structured text;
- number with bounds and units;
- boolean toggle;
- select/radio choice from code-defined options;
- safe internal or HTTPS action/link;
- media picker;
- bounded repeatable item list;
- reference picker for approved collection types.

These descriptors are enough for routine bespoke blocks and allow the existing form primitives to
be reused. A complex block may register a package-owned React editor component, but that component
still writes data validated by the package schema. There is no arbitrary schema form builder and no
customer-provided component code.

## Interactive capability model

Interactive features are classified before implementation.

### Browser-only module

Examples: mortgage calculation, ceiling-area calculation, repair estimate.

- Formula and behaviour are compiled into the Site Package.
- The CMS exposes only safe business parameters selected by the developer, such as rates, unit
  prices, minimums, maximums, and explanatory text.
- Calculation runs in the visitor's browser.
- No secret is embedded in the page.
- SEO-relevant explanation and defaults remain in rendered HTML.

### Customer runtime module

Examples: appointment availability, submission persistence, customer account, inventory lookup.

- Implemented as an explicit backend module with its own contract and threat model.
- Public endpoints live outside the CMS administration namespace.
- Authentication, rate limiting, validation, idempotency, audit, retention, and abuse controls are
  specified per capability.
- A runtime module is not implied merely because a visual block exists.

### External integration

Examples: CRM, calendar, email, Telegram, payments.

- Provider secrets remain server-side in the customer's installation secret set.
- CMS payloads contain only non-secret selections and labels.
- Webhooks and authoritative business decisions remain in backend modules.
- Failure of an external integration must not corrupt publication state.

The first Site Package acceptance fixture should use a browser-only calculator. Booking, payments,
and a generic leads inbox are separate future specifications.

## API and data flow

### Editing

1. The customer opens the installation's admin host.
2. The static web app calls that installation's `/api/cms` backend.
3. Backend authentication and capabilities are enforced exactly as today.
4. The selected package registry validates the block type and data in addition to core contracts.
5. Drafts, revisions, and package schema version are stored in that customer's database.

### Preview

1. Existing one-time preview exchange and session revalidation remain.
2. Preview renders with the same selected Site Package as production.
3. Preview never accepts a package ID from the browser.
4. Package mismatch or unknown block type fails closed with a customer-safe error in the CMS and a
   private diagnostic in server logs.

### Publication

1. Backend validates the complete candidate with core contracts and the selected Site Package.
2. Backend freezes the existing immutable publication snapshot.
3. Snapshot metadata includes the package ID, package version, and persisted schema version.
4. The builder obtains the artifact through the existing signed build flow.
5. Builder verifies snapshot package metadata against its compiled package.
6. Astro builds static output from the snapshot.
7. Media needed by that immutable revision is copied to the customer's publication destination.
8. Static files are uploaded through the existing static upload boundary.
9. Promotion verifies the revision marker before switching the live release.
10. A failed build or upload leaves the prior customer release live and exposes the existing retry
    operation.

Normal public page requests do not call `/api/cms` or a public content endpoint.

## Content and snapshot changes

The publication contract gains an explicit package descriptor:

```ts
type PublicationSitePackage = {
  id: string
  version: string
  schemaVersion: number
}
```

The exact TypeScript implementation remains subject to the implementation plan, but these semantics
are fixed:

- package ID is stable for the lifetime of a customer site;
- package version identifies deployed code;
- schema version identifies persisted payload compatibility;
- build rejects an unsupported future schema version;
- public snapshots contain no editor descriptors, secrets, server configuration, or executable
  source.

The current block payload shape stays unchanged to preserve existing data and editor operations.
Bespoke block type keys must be globally stable within the package and must not collide with core
keys.

## Versioning and migrations

Package code and persisted content evolve independently.

- A presentation-only renderer change increments package version but not schema version.
- A persisted field change increments schema version and supplies a deterministic migration.
- Migrations run as an explicit deployment step, not lazily during page rendering.
- Draft pages, settings, and reusable content are migrated transactionally.
- Immutable publication snapshots and historical revisions are not rewritten.
- Restoring an old revision first migrates its payload into a new draft, preserving history.
- Migration failure aborts deployment and leaves the currently running package and published site
  unchanged.
- Downgrade is not automatic; rollback requires a code version compatible with the current schema
  or an explicitly tested reverse migration.

The deployment records the active package ID, package version, and schema version so a later agent
can diagnose compatibility without inspecting JSON payloads.

## Media and customer-owned destination

The design distinguishes working media from published media.

- Working media is private and managed through the existing upload-ticket flow.
- Published media is an immutable copy associated with a publication revision.
- Customer destination credentials are scoped to that customer's bucket or hosting target.
- Browser clients never receive storage secret keys or private object keys.
- The studio VDS does not serve published images to site visitors.

The first certified destination is S3-compatible static hosting with immutable object paths and a
safe promotion operation. The existing Yandex Object Storage implementation is adapted behind its
existing ports rather than duplicated.

SFTP is a later destination adapter for a real customer whose hosting lacks S3. FTP, arbitrary shell
commands, and customer-provided deployment scripts are not part of the first implementation.

Operational CMS data remains in the studio-managed customer database. Customer ownership is
supported through per-customer backups and export. Moving the live CMS database to arbitrary shared
hosting is not required for this model.

## Build execution and VDS resource policy

Astro build is the main burst resource. The deployment must enforce bounded concurrency rather than
assuming customers never publish together.

For the pilot:

- one build per customer installation at a time;
- a VDS-level limit on simultaneous Astro build processes;
- explicit memory and CPU limits for customer services;
- build timeout and artifact-size limits;
- cleanup of temporary work directories on success and failure;
- Docker image and log retention limits;
- disk, memory, load, failed-build, and queue-age monitoring;
- external database and configuration backups.

The implementation plan must choose the smallest reliable cross-installation build coordination
mechanism compatible with the existing publication controller. It must not introduce Kubernetes,
Redis, or a general message broker for the pilot.

Before committing to a customer count, load tests must measure idle memory per installation, peak
build memory, build duration, disk use, and behaviour under simultaneous publish requests.

## Deployment destination abstraction

`StaticUploadPort` remains the static-file boundary. Destination support is completed as a small set
of explicit capabilities:

- upload immutable static objects;
- copy or upload immutable publication media;
- verify expected objects and revision marker;
- promote an inactive release;
- optionally purge a CDN;
- report a customer-safe failure and private diagnostic.

Provider-specific credentials and URL formats stay outside publication snapshots and package
manifests. They are deployment secrets belonging to one customer installation.

## Bootstrap and agent workflow

Creating a new customer site follows this sequence:

1. Complete `docs/CMS_SITE_BRIEF.md` with real business facts.
2. Apply `vibe-landing` and record its required `PROJECT SCOPE`.
3. Select the minimum Vibe website architecture required for the public site.
4. Create a new Site Package from the supported package starter.
5. Reuse core blocks where their semantics fit.
6. Add bespoke blocks or browser modules only for real site requirements.
7. Define customer-editable fields and keep design/programming fields code-owned.
8. Add package defaults and idempotent initial content bootstrap.
9. Run package compatibility, CMS editor, snapshot, Astro build, and browser tests.
10. Configure the customer's isolated installation and publication destination.
11. Deploy without granting repository or server-shell access to the CMS customer.

The existing neutral `/cms-demo` fixture remains a core CMS lifecycle test. It is not a customer
design starter and does not become a mandatory visual template.

## Security boundaries

- No arbitrary HTML, CSS, JavaScript, iframe, remote component URL, or executable manifest field.
- No runtime package selection from customer data.
- No customer-selected database, bucket, or deployment destination identifier in ordinary CMS
  requests.
- Each process receives least-privilege credentials for one installation.
- Builder authentication, timestamp, nonce, artifact limits, immutable snapshots, and safe object
  paths remain enforced.
- CORS permits only the installation's admin and preview origins.
- Runtime public APIs use separate routes and policies from authenticated CMS APIs.
- Logs identify installation and publication revision but do not contain content payloads, tokens,
  secrets, signed URLs, or customer personal data.
- Backups are encrypted, access-controlled, tested for restore, and retained per customer policy.

## Failure handling

- Unknown package or package mismatch: installation and build fail closed before mutation or
  promotion.
- Invalid bespoke block data: field-level CMS correction; draft is not silently coerced.
- Unsupported snapshot schema: build fails and prior release stays live.
- Failed content migration: deployment stops before application promotion.
- Destination upload failure: inactive release is abandoned; prior release stays live.
- Marker or promotion verification failure: publication remains failed/retryable and is not marked
  published.
- External integration failure: affects only that runtime action, not CMS content publication.
- Customer hosting unavailable: publication retries according to existing bounded retry policy;
  existing live files remain untouched.
- VDS or CMS outage: already published static sites remain available; editing, preview, and new
  publication are temporarily unavailable.

## Testing and acceptance criteria

### Registry and contracts

- A selected package can allow, hide, override, and extend core blocks without editing CMS core
  switch statements.
- Unknown and colliding block types are rejected.
- Descriptor defaults pass the matching schema.
- Package and snapshot version mismatches fail closed.
- Public snapshots omit editor descriptors, secrets, and private fields.

### Admin

- Add/remove/reorder/duplicate behaviour remains green for permitted blocks.
- Hidden blocks cannot be inserted through UI or direct API requests.
- Descriptor fields render accessible Russian labels, hints, errors, and bounded controls.
- A package-owned complex editor cannot save data that fails its registered schema.
- Preview uses the same renderer and package version as publication.

### Website and interaction

- Core blocks render through a package's bespoke design.
- A bespoke calculator block renders SEO-visible explanation in HTML and calculates in the browser.
- Browser modules contain no server secret and function without the CMS API.
- Mobile and desktop browser QA covers navigation, media, calculator interaction, keyboard flow,
  overflow, heading order, metadata, and reduced motion.
- Images reserve dimensions and use appropriate responsive loading behaviour.

### Publication and destination

- A known snapshot builds against the matching package.
- A mismatched package never uploads or promotes output.
- Static and media objects are confined to the configured customer destination.
- Failed upload or promotion retains the previous release.
- Public HTML loads successfully while the CMS API is unavailable.
- Multiple quick publications converge on the newest desired revision.

### Isolation and operations

- Customer database roles cannot access another customer's database.
- Customer destination credentials cannot write another customer's paths.
- Admin origins cannot call another installation's CMS API.
- Simultaneous publication load remains within configured VDS memory limits or queues without
  corrupting state.
- Backup restore is demonstrated for one isolated installation before production onboarding.

## Out of scope for the first implementation

- One database shared by all customers with `tenantId` row filtering.
- Customer-selectable themes or package switching.
- Generic no-code formulas, workflows, or backend modules.
- Arbitrary custom code entered through the CMS.
- Marketplace installation of third-party packages.
- Customer repository or server-shell access.
- License server, DRM, code obfuscation, or source-code buyout workflow.
- Booking, payments, CRM inbox, and generic form-delivery product.
- Kubernetes, Redis, or a new general-purpose message broker.
- FTP and arbitrary deployment scripts.
- Guaranteed capacity expressed as a fixed number of customer sites before load measurement.

## Implementation-plan boundaries

The implementation plan following this specification must be phased so every phase leaves existing
CMS tests and publication behaviour working. It must clearly separate:

1. package contracts and registry extraction;
2. admin registry consumption;
3. website renderer selection;
4. package versioning and migration;
5. customer destination adapters;
6. isolated installation/deployment configuration;
7. build resource coordination;
8. reference Site Package and end-to-end validation;
9. agent workflow, operations, backup, and handoff documentation.

No phase may solve multi-tenancy, generic plugin execution, or new business runtime APIs as an
incidental prerequisite.
